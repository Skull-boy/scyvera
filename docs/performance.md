# Performance

How long does `scyvera audit` take on a repository of a given size? This page
answers that with a table, a method, and the hardware it ran on — or with an
explicit "not measured". It is not a comparison: no other tool was measured, and
nothing here can support one.

The protocol was written before the numbers and is implemented by the scripts in
[`benchmarks/`](../benchmarks/). The table below is generated by
`benchmarks/render.py` from the stored result JSON, never hand-copied, so it
cannot drift from the evidence.

## What is measured

| Metric | Definition |
|---|---|
| `end_to_end_ms` | Wall clock of one `python -m scyvera.cli audit <tree> --json` subprocess, from spawn to exit. Interpreter startup is included: that is what a CI user feels. |
| `scan_ms` | The same work measured in-process around `scyvera.audit.scan_tree` (the public report entry point). Differences from `end_to_end_ms` are startup and process overhead, not hidden work. |
| `peak_rss_mb` | The child process's peak resident set. Windows: `GetProcessMemoryInfo` → `PeakWorkingSetSize`. Linux: `/proc/<pid>/status` → `VmHWM`. macOS: `resource.getrusage(RUSAGE_CHILDREN).ru_maxrss`, which is a high-water mark across children (bytes on macOS, KiB on Linux); it is labelled as a bound, not a per-run measurement. |
| `files_scanned` / `files_skipped` | From the report's own `stats`. A file is skipped when it is over 1 MiB, binary (NUL in the first 8 KiB), a symlink, or inside a skipped directory. |
| `bytes_scanned` | Sum of the sizes of the files the report counted as scanned. Bytes matter as much as file count: the 1 MiB cap means a "10,000-file repository" of 200-byte files is not the same amount of work as one of 2 KiB files. |
| `findings` | Findings in the report, including governed and quarantined ones. |

`python -m scyvera` is not an entry point in this package (there is no
`__main__.py`), so the measured command is `python -m scyvera.cli audit`, which is
the module the `scyvera` console script calls.

## Protocol

1. One discarded warm-up run.
2. `N = 10` timed end-to-end runs. The headline is the **median**, never the best
   run; `min`, `p95`, and `max` are published beside it.
3. `p95` uses linear interpolation (the numpy `linear` definition) over the ten
   samples; `p95/median` is published so variance is visible rather than implied.
4. In-process scans: one discarded warm-up, then 3 timed samples per cell. The
   end-to-end number is the headline; the in-process number is supporting
   evidence and its smaller sample count is stated here, not hidden.
5. Every cell is verified before its number is trusted: the parsed report must
   show exactly the `files_scanned`/`files_skipped` the generator created, the
   harness must independently agree on scanned and skipped bytes, and two
   consecutive `--json` runs must be byte-identical. A cell that fails
   verification is reported as `invalid` and stops the run; no number is
   published from it.

## Cache state

All numbers are **warm-filesystem-cache**. Cold-cache was not measured: dropping
the page cache needs privileges that are not available on the development machine
or on a hosted runner without root, and a synthetic "cold" run that only clears
the process's own buffers would misrepresent the result. A cold run will be
slower by an amount this page does not claim to know.

## Corpora

Corpora are generated, seeded, and deterministic: the same seed produces
identical paths and contents, asserted by hashing the tree manifest in
`tests/test_benchmark_harness.py`. Nothing is committed; generation refuses any
destination inside the checkout.

| Property | Value |
|---|---|
| Average text file | ~2 KiB (uniform 1–3 KiB) |
| Over-cap files | 5% of files at 1.2 MiB, so the 1 MiB cap skips them |
| Binary files | 2% of files (NUL byte in the first 8 KiB) |
| Nesting | up to depth 8 |
| Extension mix | 42% source (`.py`, `.ts`, `.js`, `.go`, `.rs`), 50% text (`.txt`, `.md`), 8% `.json` |
| Skipped-directory decoys | `node_modules/`, `.git/`, `build/`, `dist/`, `.venv/`, each containing rule-triggering text that must not affect findings or counts |

Profiles:

- **`clean`** — filler only; the harness fails the cell if any rule matches.
- **`noisy`** — one file per AUxxx rule, so all twelve rules fire; the harness
  fails the cell if any rule is missing.
- **`governed`** — `noisy` plus a valid root `contract.yaml` that declares and
  approves `registry:publish`, exercising the RFC 0004 Amendment 2 path; the
  harness fails the cell if nothing is governed.

`--files N` counts every regular file the generator creates, including the
over-cap and binary files that the scan will skip.

## Scales and budget

Scales are 1,000 / 5,000 / 10,000 / 50,000 files. Each profile's ladder is
measured in ascending order with a **1,200-second budget per cell**.

- Before a cell runs, its cost is projected from the measured smaller cell:
  `median_smaller × (scale / smaller_scale) × runs`. If the projection exceeds
  the budget, the cell is recorded as `not_measured` with the formula and the
  basis, and **no corpus is generated for it**.
- If a cell's own warm-up projects over budget, it is also recorded as
  `not_measured` with that fact.
- A cell that stops (warm-up over budget) ends that profile's ladder. Every
  larger requested scale is then recorded as `not_measured` with reason
  `ladder_stopped`, naming the cell that stopped it and that cell's reason. No
  corpus is generated for those scales, and they still appear in the table.
- Missing rows are published in the table. They are not dropped, and they are
  not interpolated into a number.

## Claim policy

Allowed, and only in this shape:

> On <hardware>, <date>, at commit <sha>, scanning <bytes> across <n> files took
> <median> ms (p95 <x> ms).

Forbidden:

- Comparisons to other scanners, or to `scyvera-ts` / `scyvera-rs` (different
  code, different work, not like-for-like).
- Extrapolation to 1,000,000 files or any unmeasured scale.
- "Fast", "blazing", "instant", or any adjective in place of the number.
- Any figure without its environment block, repeat count, and cache state.
- A best-of-N number presented as the result.

## Limits

- **Warm cache only** — see above; cold-start behaviour is unmeasured.
- **Single-threaded scan** — the audit walks and parses on one thread; the
  numbers say nothing about parallel throughput.
- **Two environments** — a Windows developer machine and `ubuntu-latest` on
  GitHub Actions. No macOS, ARM, or container numbers.
- **No comparison to other tools**, and none to the TypeScript or Rust runtimes.
- **Bytes ≠ files** — 5% of the corpus is over the 1 MiB cap and skipped, so the
  scanned byte count is smaller than the bytes on disk. The `skipped` column is
  part of the result, not an omission.
- **Synthetic corpora** — the mix is stated above. Real repositories differ in
  file size distribution, extension mix, and encoding; this page does not claim
  to predict them.
- **Budget stops are data** — any `not measured` row states its basis: the
  projection formula, the warm-up overrun, or the ladder stop that ended the run
  above it. It is not an implied pass.

## Reproduce

```bash
# 1. Generate one corpus (refuses to write inside the repository)
python benchmarks/gen_corpus.py --out /tmp/scyvera-bench-1k --files 1000 --profile noisy --seed 5

# 2. Measure (writes the result JSON; also prints the table)
python benchmarks/run.py --files 1000,5000,10000 --profiles noisy --repeats 10 --json /tmp/result.json

# 3. Render the table that belongs on this page
python benchmarks/render.py /tmp/result.json
```

The `Performance benchmark` workflow runs the same harness with
`workflow_dispatch` only, uploads the JSON as an artifact, and writes nothing
back to the repository.
